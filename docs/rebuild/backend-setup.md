# Academy backend activation and operations

The code runs without credentials and reports online booking/payment unavailable. Production never substitutes the recruiter sandbox. Local PostgreSQL tests verify the migration and transaction invariants; they do not establish working Supabase OAuth, SMTP, Razorpay mandates, refunds or deployed webhooks. Those require the final activation gate below.

## Clean database and auth

1. Create a new Supabase project on a supported current PostgreSQL version. Apply only `supabase/migrations/20261003054531_academy_core.sql`, never the legacy `supabase/schema.sql`. The migration creates the four academy courts and all business tables with RLS enabled and no anon/authenticated business grants. `academy_dispatch(text,jsonb,uuid)` and its helpers are service-role only, with security invoker; the server obtains identity from verified Supabase `getUser()` and reads staff role from the private academy customer table.
2. Set the new project's URL, publishable key, service-role key and canonical site URL in private deployment environment settings. Keep both academy enable switches false while applying schema. A stale old URL does not enable the new backend. Service-role and Razorpay secrets must never use `NEXT_PUBLIC_` names or be pasted into chat, logs, source, screenshots or commits.
3. Configure Supabase Auth Site URL and the exact production `/auth/callback` redirect URL. Add localhost callback only for local development. Enable Google OAuth with the new project's callback on Google's credential settings. Configure custom SMTP, sender domain authentication and email magic links. This project was created on the free tier after Supabase's June 3, 2026 change that locks default auth email templates for new free projects; branded templates require custom SMTP. A zero-monthly-cost candidate checked October 4 is Brevo Free, which currently includes SMTP transactional email up to 300 sends/day; it requires an authenticated sender domain and SMTP credentials. It has not been selected or provisioned. Confirm free-tier limits and domain requirements before activation; do not upgrade Supabase or start a paid email plan under the current zero-cost constraint. [Brevo free plan](https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans) · [Brevo SMTP setup](https://help.brevo.com/hc/en-us/articles/7924908994450-Send-transactional-emails-using-Brevo-SMTP). For PKCE links, open the link in the requesting browser. A cross-device template can use `/auth/callback?token_hash={{ .TokenHash }}&type=email&next=/app`; do not blindly forward arbitrary external return URLs. The callback accepts only academy paths and preserves selected court/time intent.
4. Enable both switches in a private staging environment and sign in the owner's real account. Every authenticated request repairs a missing academy customer row; metadata can supply a display name, never staff authorization. From the private Supabase SQL editor, locate that account in `academy_customers` and assign its role `owner`; assign trusted staff `staff` individually. There is no public bootstrap, seed-owner or recruiter operator login.
5. Generate real database types from the provisioned schema and compare them with `lib/academy/database-types.ts`. Current types are hand-maintained migration contracts, not generated verification. Run Supabase security/performance advisors and inspect Data API grants. The optional retirement block also revokes known dangerous legacy RPCs if applied to an existing database, but a clean project remains the intended setup.

Official guidance: [Supabase SSR clients](https://supabase.com/docs/guides/auth/server-side/creating-a-client), [SSR session freshness and caching](https://supabase.com/docs/guides/auth/server-side/advanced-guide), [securing the Data API](https://supabase.com/docs/guides/api/securing-your-api). The September 2026 [PostgreSQL minor-upgrade notice](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes) affects existing btree_gist indexes; fresh academy indexes avoid carrying an old operator definition forward.

## Razorpay test configuration

- Set `ACADEMY_PAYMENT_MODE=test`, test key ID/secret, and webhook secret. Configure automatic capture. Court orders are created on the server with integer paise, INR, immutable amount, unique attempt receipt and private attempt note. Browser confirmation must pass HMAC verification and an API-fetched captured payment matching the persisted order/amount/currency. Authenticated payment alone is insufficient. An expired/cancelled hold cannot be revived: a late captured payment creates a durable refund job.
- Create a monthly interval-one INR2500 plan; set its plan ID. The server checks the fetched plan amount/currency/cadence before subscription creation. Razorpay requires a finite `total_count`; this implementation uses 120 monthly cycles (ten years) with auto-renewal until cancellation/completion. There are no free court entitlements or banked credits. Benefits start only after an API-fetched captured INR2500 payment on a paid subscription invoice with a verified billing period. The unpaid authentication charge and `subscription.activated` event alone grant nothing.
- Enable endpoint `https://<canonical-host>/api/payments/webhook` for `payment.captured`, subscription lifecycle events (especially `subscription.charged`, pending/halted/cancelled/completed), and refund events. Use the original raw body signature and `x-razorpay-event-id`. Rotate webhook secrets with the previous-secret environment slot until older retries are exhausted. Never log payment payloads; stored event payloads are private and access-restricted.
- Court and subscription creation are not assumed provider-idempotent. The database allows only one attempt per reservation/membership and serializes pending membership creation. An ambiguous provider timeout is preserved for reconciliation; another provider entity is not blindly created. The bounded history scan finds `academy_attempt_id` notes. If the entity falls beyond the scan or was never created, staff must inspect provider history before resolving the attempt. Refund requests use Razorpay's documented `X-Refund-Idempotency` header with the durable refund job UUID.

Official references: [court checkout verification](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/), [webhook verification/retries](https://razorpay.com/docs/webhooks/validate-test/), [subscription creation](https://razorpay.com/docs/api/payments/subscriptions/create-subscription/), [paid subscription invoices](https://razorpay.com/docs/api/payments/subscriptions/fetch-invoices), [cycle-end cancellation](https://razorpay.com/docs/api/payments/subscriptions/cancel-subscription/), [idempotent refunds](https://github.com/razorpay/markdown-docs/blob/master/api/refunds/normal-refunds-idempotent.md).

## Scheduling, refunds and staff records

Configure a scheduler to call `GET /api/cron/reconcile` every five minutes with `Authorization: Bearer <CRON_SECRET>`. It expires holds and processes bounded payment, refund, cancellation and failed-webhook batches. Deploy this endpoint on a runtime supporting its 120-second maximum duration. Returned nonzero `failed`/`unresolved` counts require monitoring; create an alert outside the public site. Attempts are processed fairly by their last reconciliation time; failed events have backoff and unfinished event leases can recover. Provider webhook delivery remains the primary payment signal, scheduler reconciliation is recovery. The read/hold paths also repair expired holds; public availability generates the rolling fourteen-day grid from real allocations, so it has no stale seeded slots. Netlify is under consideration for zero-cost staging and supports Next.js App Router, but its scheduled functions have a 30-second execution limit; this endpoint cannot be assumed compatible at its declared 120-second maximum. Evaluate a compatible scheduler/runtime or make and test a bounded-work change before scheduling it. Do not let a deployment provider's free tier incur usage charges; document any quota-based suspension/no-SLA behavior.

Staff cancellation requires a reason, accepts zero/full/partial refund, releases occupancy atomically and preserves a pending gateway refund until provider confirmation. A refund API failure does not silently claim the money returned. Check pending `academy_refunds`, failed `academy_webhook_events`, reconciliation attempts and `academy_audit` daily. A processed refund is recorded once. Additional captured payments on an already settled booking are refunded separately and cannot change the reservation or falsely refund its original valid payment.

Manual walk-ins/phone/platform records default to unpaid. Staff explicitly records cash/external/not-required with a reference or reason; Playo/Hudle/District requires its platform reference. No automatic external synchronization is claimed. Schedule “Recorded receipts” totals include recorded external payments, cash and verified gateway captures; refunds include recorded external/cash returns and processed gateway refunds, including duplicate/late captures. They do not imply bank settlement.

Member individual-play reservations are staff-only. A zero-priced linked member session must fall today, be covered by paid membership, and atomically consume that member's daily attendance. A previously recorded standalone visit consumes the included benefit, so a further free reservation is refused. Paid court bookings remain INR400 for a paid member whose membership covers the chosen start, INR500 otherwise. Staff amount overrides require a reason. Retaining a recurring subscription after missed renewal prevents creating a competing mandate: it becomes past_due with no benefits until a paid invoice arrives, or the member cancels and rejoins. Cancellation requests survive provider/database interruptions and are reconciled; paid-through access remains until the verified paid period ends.

## Final live gate

Run tests, lint, typecheck, production build and local PostgreSQL scenarios. Then verify staging using two independent customer accounts and a staff account: real email/Google callbacks and return intent; cross-customer isolation; parallel holds; maintenance races; expiry; captured/failed payments; repeated callbacks and webhooks; late payment with replacement booking; partial/full and repeated refunds; membership mandate, initial paid invoice, renewal failure/recovery, cancellation, daily attendance and repeated free-session rejection. Validate public payloads contain no customer/payment data and anon/authenticated roles cannot execute academy RPCs or mutate business tables.

Only after Razorpay account/subscriptions activation, club payment identity, deployment inputs and real staging evidence are complete should the owner enable live keys and `ACADEMY_PAYMENT_MODE=live`. Keep the club contact separate from any owner's private payment contact. The environment template contains names and disabled defaults only; no credentials are supplied by this implementation.
